# Platform Engineering Roadmap

## Purpose

This roadmap describes how the application is built, released, deployed, secured, observed, and operated.

Application and data capabilities are defined in the [Application Roadmap](0.application-roadmap.md). The reliability evidence expected from both roadmaps is defined immediately after this document in [Reliability Consolidation](2.reliability-consolidation.md).

## Phase 1 - Container Build And Software Supply Chain

Status: partially implemented.

Goal: produce reproducible, traceable, and efficiently built runtime images.

Actions:

1. Cache dependency installation separately from application changes.
2. Use BuildKit cache mounts and registry-backed CI caches.
3. Keep heavy Airflow and Spark runtime dependencies isolated by image or target.
4. Run image smoke tests for critical imports and entrypoints.
5. Pin image and dependency inputs.
6. Scan the filesystem and container image.
7. Generate an SBOM for published images.
8. Link image metadata to source revision and release version.

Deliverables:

- optimized application, Airflow, and Spark images;
- registry build cache;
- runtime smoke tests;
- vulnerability reports;
- SBOM and OCI metadata.

## Phase 2 - CI/CD Quality Gates

Status: partially implemented.

Goal: encode validation and promotion rules in CI/CD.

Actions:

1. Run formatting, linting, strict typing, unit tests, coverage, and dependency audits on changes.
2. Run integration lanes against Kafka, Schema Registry, Airflow, and Spark according to change risk.
3. Build and scan immutable images on mainline changes.
4. Run secret and workflow scanning.
5. Publish test, coverage, security, and integration reports as artifacts.
6. Keep promotion steps traceable.
7. Add changed-code and critical-module quality thresholds.

Deliverables:

- required PR quality workflow;
- integration workflow;
- image build and security workflow;
- promotion gate checklist;
- retained CI evidence.

## Phase 3 - Release Engineering

Status: planned.

Goal: make every promoted version immutable, documented, and traceable.

Actions:

1. Choose and document the versioning strategy.
2. Generate release notes from reviewed changes.
3. Support release candidates before stable promotion.
4. Publish immutable image tags and digests.
5. Link releases to source SHA, test results, security reports, SBOM, and deployment target.
6. Build and publish versioned documentation.
7. Define rollback eligibility and known-good versions.

Deliverables:

- versioning policy;
- automated release notes;
- prerelease and stable-release workflows;
- release evidence bundle;
- versioned documentation.

## Phase 4 - Kubernetes Deployment

Status: planned.

Goal: deploy workloads through a repeatable and hardened runtime model.

Actions:

1. Use a Kubernetes CronJob for the first production-shaped ingestion runtime.
2. Version deployment manifests in Git.
3. Deploy immutable image references.
4. Inject non-secret configuration through ConfigMaps.
5. Inject secrets through Kubernetes or an external secret manager.
6. Define resource requests, limits, probes, and termination behavior.
7. Use `concurrencyPolicy: Forbid` until concurrent execution semantics are proven.
8. Document deployment, smoke test, rollback, and suspension operations.
9. Define the production topology for Airflow and Spark before deploying them.

Target progression:

| Phase | Runtime |
|---|---|
| 1 | Kubernetes CronJob + Kafka + Schema Registry |
| 2 | Airflow + Kafka + Schema Registry |
| 3 | Airflow + Kafka + Spark |
| 4 | Airflow + Kafka + Spark + Cassandra |

Deliverables:

- versioned Kubernetes manifests;
- environment configuration pattern;
- deployment and rollback commands;
- post-deployment smoke tests;
- runtime hardening checklist.

## Phase 5 - Observability And SLOs

Status: partially specified.

Goal: make platform behavior diagnosable and use operational signals to govern releases.

Actions:

1. Centralize structured logs with correlation identifiers.
2. Emit counters for ingestion, quality outcomes, publication, processing, and storage.
3. Emit latency histograms and consumer-lag metrics.
4. Define SLIs before dashboards.
5. Define SLOs and error-budget alerts.
6. Alert on user-visible symptoms and sustained burn rather than raw resource use alone.
7. Add post-release monitoring checks.
8. Define telemetry retention and access.

Initial SLO candidates:

| SLI | Initial objective |
|---|---:|
| Ingestion success rate | >= 99% over 24h |
| Kafka publication success rate | >= 99% over 24h |
| Kafka publication latency | p99 < 30s over 24h |
| Invalid-event completeness | 100% include rejection reasons |
| Secret hygiene | zero known committed secrets |

Deliverables:

- SLI/SLO specification;
- metrics naming convention;
- dashboards and alerts;
- post-release verification checklist.

## Phase 6 - Day-Two Operations

Status: planned.

Goal: make routine and incident operations repeatable.

Actions:

1. Document startup, shutdown, deployment, suspension, and rollback.
2. Document Kafka topic and Schema Registry diagnostics.
3. Document Airflow failed-run and Spark checkpoint diagnosis.
4. Document safe replay and rerun procedures.
5. Document source API, Kafka publication, processing, and storage incidents.
6. Define incident roles, escalation, and evidence collection.
7. Define dependency and base-image patch cadence.
8. Maintain backup and restoration procedures for persistent components.

Deliverables:

- service runbooks;
- incident-response checklist;
- replay and rollback procedures;
- patching policy;
- operational ownership matrix.

## Phase 7 - Continuous Security

Status: partially implemented.

Goal: integrate security controls into delivery and runtime operations.

Actions:

1. Keep dependency, filesystem, image, workflow, and secret scanning active.
2. Time-bound and review security exceptions.
3. Run workloads as non-root.
4. Use a read-only root filesystem where practical.
5. Drop Linux capabilities and apply seccomp.
6. Apply least-privilege ServiceAccounts and RBAC.
7. Apply default-deny NetworkPolicies and explicit allowed flows.
8. Require TLS and managed service credentials in shared environments.
9. Rotate credentials and certificates.
10. Prevent secrets and raw invalid payloads from entering logs.
11. Validate manifests through policy-as-code in CI.

Deliverables:

- security workflows and exception policy;
- RBAC and network-flow matrices;
- secret and certificate lifecycle documentation;
- policy-as-code reports;
- production hardening evidence.

## Platform Delivery Order

| Increment | Capability | Exit criterion |
|---|---|---|
| 1 | Reproducible supply chain | images are traceable, scanned, and accompanied by an SBOM |
| 2 | CI/CD gates | required quality and security evidence blocks unsafe promotion |
| 3 | Release engineering | releases link immutable artifacts and validation evidence |
| 4 | Kubernetes deployment | deployment and rollback are repeatable |
| 5 | Observability | SLO indicators and alerts are operational |
| 6 | Day-two operations | common incidents and replay operations have tested runbooks |
| 7 | Runtime security | least privilege, network isolation, TLS, and rotation are enforced |

## Platform Definition Of Done

The platform roadmap is complete when:

1. Runtime artifacts are reproducible, immutable, scanned, and traceable.
2. CI/CD retains the evidence required for promotion.
3. Releases connect source, image, SBOM, tests, security, and deployment metadata.
4. Kubernetes deployment, smoke testing, rollback, and suspension are documented and repeatable.
5. SLO indicators, dashboards, and alerts cover the critical data path.
6. Runbooks cover routine operations, replay, dependency failure, and persistent recovery.
7. Runtime access and network paths follow least privilege.
8. Platform controls required by Reliability Consolidation are implemented and testable.
