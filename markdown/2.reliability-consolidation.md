# Reliability Consolidation

This is the third roadmap document, read directly after the [Platform Engineering Roadmap](1.platform-engineering-roadmap.md).

Roadmap sequence:

1. [Application Roadmap](0.application-roadmap.md)
2. [Platform Engineering Roadmap](1.platform-engineering-roadmap.md)
3. Reliability Consolidation

## Purpose

This document complements the application-oriented development roadmap.

The development roadmap describes what the platform builds: ingestion, Kafka messaging, Airflow orchestration, Spark processing, Cassandra persistence, CI/CD, and deployment.

This consolidation plan describes what the platform must prove:

- processing remains correct under concurrency, retry, restart, and replay;
- overload and dependency failures remain contained;
- access, traffic, secrets, and audit evidence are protected;
- capacity and recovery objectives are measured;
- operational assumptions are validated through restoration and chaos exercises;
- data retention, deletion, and pseudonymization are controlled.

The target is not to claim perfect availability or end-to-end exactly-once processing. The target is an explicit, measurable, and tested reliability model for an at-least-once distributed data platform.

| Reliability capability | Gap |

| Deduplication | no stable event identity or end-to-end deduplication policy |
| Backpressure | no flow-control policy across ingestion, Kafka, Spark, and storage |
| Circuit breaking | retries exist, but dependency state and retry budgets are not coordinated |
| Kubernetes isolation | RBAC and NetworkPolicies are not yet defined |
| Auditability | application logs are structured but not immutable security audit records |

## Consolidation Pillars

### Pillar 1 - Processing Correctness

Objective: make event processing deterministic and safe under retry, concurrency, restart, and replay.

Key changes:

1. Add immutable `event_id`, `event_version`, `occurred_at`, and correlation metadata to event contracts.
2. Document the end-to-end semantic as at-least-once delivery with idempotent processing.
3. Define ordering guarantees and the Kafka partition key strategy.
4. Define deduplication identities and windows for ingestion, Spark, replay, and Cassandra.
5. Add Spark event-time watermarking and deduplication where justified by the data flow.
6. Make persistent writes idempotent using documented business and event keys.
7. Test concurrent producers, overlapping jobs, consumer restart, checkpoint recovery, and replay during live processing.

Required evidence:

- processing-semantics ADR;
- duplicate injection and replay tests;
- deterministic concurrency scenarios;
- no unintended duplicate final state after replay.

### Pillar 2 - Controlled Flow And Dependency Failure

Objective: stop overload or a degraded dependency from creating an uncontrolled cascade.

Key changes:

1. Define ingestion rate, producer queue bounds, batch size, Spark trigger interval, and maximum consumer rate.
2. Measure producer queue depth, consumer lag, batch duration, throttling, retries, and rejected events.
3. Introduce dependency-specific retry budgets with exponential backoff and jitter.
4. Add circuit breakers where synchronous calls can amplify failure.
5. Define the fallback for each dependency: pause, fail, preserve offsets, retry later, or route to a DLQ.
6. Define overload recovery criteria before introducing autoscaling.
7. Add a cache only after a load test demonstrates a concrete bottleneck and the invalidation model is documented.

Required evidence:

- saturation and dependency-degradation tests;
- backpressure and lag dashboard;
- circuit-breaker metrics;
- fallback decision table and runbook.

### Pillar 3 - Secure Platform Runtime

Objective: deploy workloads with least privilege, explicit connectivity, and managed service identity.

Key changes:

1. Create dedicated Kubernetes ServiceAccounts for ingestion, Airflow, Spark, and operational jobs.
2. Add namespace-scoped RBAC without wildcard permissions.
3. Apply default-deny ingress and egress NetworkPolicies.
4. Allow only documented flows to Kafka, Schema Registry, Cassandra, telemetry, DNS, and the source API.
5. Enforce non-root execution, a read-only root filesystem, dropped capabilities, seccomp, and resource bounds.
6. Store shared-environment secrets in an external secret manager.
7. Require TLS for internal and external service communication in shared environments.
8. Define certificate issuance, trust distribution, expiry monitoring, and rotation ownership.
9. Exercise credential and certificate rotation without losing or duplicating events.

Required evidence:

- RBAC matrix and network-flow matrix;
- policy-as-code validation in CI;
- negative authorization and connectivity tests;
- successful credential and certificate rotation exercise.

### Pillar 4 - Observability, Audit, And Capacity

Objective: make platform health, security-relevant actions, and supported capacity measurable.

Key changes:

1. Define SLIs for end-to-end latency, success rate, consumer lag, duplicate rate, and recovery.
2. Define SLOs and error-budget alerts from those SLIs.
3. Separate operational application logs from security audit events.
4. Audit deployments, configuration changes, replays, schema changes, administrative access, rotations, and deletion requests.
5. Export audit events to access-controlled append-only or tamper-evident storage.
6. Define steady-state, peak, burst, replay, and degraded-dependency load profiles.
7. Measure throughput, latency, lag, errors, resource use, network use, and storage growth.
8. Publish the saturation point, safe operating capacity, scaling assumptions, and reserved headroom.

Required evidence:

- SLI/SLO specification and dashboards;
- audit-event schema and immutable-retention policy;
- versioned load-test scenarios;
- capacity report with tested limits and scaling recommendations.

### Pillar 5 - Recoverability And Chaos

Objective: prove that persistent state and processing can be restored within agreed limits.

Key changes:

1. Classify Kafka topics, offsets, Spark checkpoints, schemas, Airflow metadata, Cassandra data, and deployment configuration as recoverable state.
2. Define an RPO and RTO for each state class and for the complete pipeline.
3. Align replication, retention, checkpoint storage, backups, and infrastructure-as-code with those objectives.
4. Automate backup verification and restoration into an isolated environment.
5. Document recovery order, ownership, dependencies, and communication.
6. Run scheduled restoration exercises and record measured RPO/RTO.
7. Inject controlled Kafka, Spark, Schema Registry, Cassandra, DNS, API, latency, packet-loss, and connection-reset failures.
8. Define a hypothesis, blast radius, abort condition, and expected signal for every chaos experiment.

Required evidence:

- approved RPO/RTO matrix;
- disaster-recovery plan;
- automated restore test and dated exercise report;
- versioned chaos experiments and remediation backlog.

### Pillar 6 - Data Lifecycle And Engineering Governance

Objective: control data exposure and keep reliability decisions reviewable.

Key changes:

1. Classify fields and topics by sensitivity and operational purpose.
2. Define Kafka retention and compaction settings per topic.
3. Define Cassandra TTL, tombstone, compaction, repair, and deletion implications.
4. Keep raw personal data out of invalid events, logs, metrics, and audit records.
5. Version pseudonymization rules and define salt or key rotation behavior.
6. Define deletion propagation across topics, derived data, Cassandra views, backups, and audit evidence.
7. Add source-to-Kafka-to-Spark-to-Cassandra end-to-end tests when persistence is introduced.
8. Cover valid, invalid, duplicate, replay, restart, dependency failure, and recovery paths.
9. Add changed-code and critical-module coverage thresholds alongside the global threshold.
10. Version context, component, deployment, and data-flow diagrams.
11. Record architectural decisions for event identity, processing semantics, partitioning, checkpoints, secrets, recovery, retention, and topology.

Required evidence:

- data inventory and retention matrix;
- deletion and pseudonymization runbooks;
- end-to-end CI lane and risk-based quality gates;
- architecture diagrams and ADR index.

## Delivery Sequence

The consolidation should progress through evidence-producing increments.

| Increment | Scope | Exit criterion |
|---|---|---|
| 1. Correctness | event identity, ordering, deduplication, concurrency, replay | replay and restart create no unintended duplicate final state |
| 2. Secure runtime | Kubernetes, RBAC, NetworkPolicies, secrets, TLS | unauthorized access is denied and rotation succeeds |
| 3. Controlled degradation | backpressure, retry budgets, circuit breakers, fallbacks | dependency degradation remains bounded and observable |
| 4. Known capacity | load testing and capacity model | supported load and saturation limits are published |
| 5. Recoverability | RPO/RTO, backups, restore automation, DR | measured restoration meets approved objectives |
| 6. Resilience validation | chaos experiments and full E2E failure paths | expected failures are detected, contained, and recovered |
| 7. Data governance | retention, deletion, pseudonymization lifecycle | lifecycle controls are documented and tested |

## Reliability Definition Of Done

The project can present itself as an SRE/Data Platform reliability demonstrator when:

1. Processing semantics, event identity, ordering, deduplication, and replay behavior are documented and tested.
2. Concurrent execution, restart, and replay do not create uncontrolled duplicate final state.
3. RBAC and NetworkPolicies follow least privilege and have negative tests.
4. Shared-environment traffic uses TLS and credential or certificate rotation has been exercised.
5. Backpressure, lag, retry budgets, circuit breakers, and fallbacks are observable and tested.
6. Throughput, latency, saturation, scaling assumptions, and capacity headroom are published.
7. RPO and RTO are approved and met during a dated restoration exercise.
8. Kafka, Spark, network, and persistent-store failures have controlled chaos experiments.
9. Audit events are separated from application logs and retained with tamper-evident controls.
10. Retention, deletion, and pseudonymization lifecycle controls are documented and tested.
11. End-to-end tests cover normal processing, invalid data, duplicates, replay, restart, and selected failures.
12. Architecture diagrams, ADRs, runbooks, and operational evidence are versioned with the implementation.
