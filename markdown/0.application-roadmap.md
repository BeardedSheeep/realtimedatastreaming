# Application Roadmap

## Purpose

This roadmap describes what the application and data pipeline build.

The product scope remains deliberately narrow: fetch demo user profiles, normalize and validate them, publish explicit events, process them as a stream, and persist queryable views.

Platform delivery and operational controls are defined in the [Platform Engineering Roadmap](1.platform-engineering-roadmap.md). Cross-cutting reliability guarantees are defined in [Reliability Consolidation](2.reliability-consolidation.md).

## Target Data Flow

```text
Random User API
        |
        v
Python ingestion and quality validation
        |
        v
Kafka + Schema Registry
        |
        v
Spark Streaming validation and routing
        |
        v
Cassandra query views

Airflow orchestrates scheduled execution, retries, and backfills.
```

## Product Boundary

### In Scope

1. Fetch profiles from Random User.
2. Normalize profiles into a stable `UserCreated` contract.
3. Validate structural and semantic quality.
4. Publish valid and invalid events to dedicated Kafka topics.
5. Govern Kafka contracts through Schema Registry.
6. Keep invalid events privacy-reduced.
7. Orchestrate the pipeline with Airflow.
8. Process and route events with Spark Streaming.
9. Persist queryable profile and quality views in Cassandra.
10. Validate component boundaries through deterministic and integration tests.

### Out Of Scope

1. Multi-source ingestion.
2. Full analytical dashboards.
3. Complex enrichment pipelines.
4. A cache without a measured application use case.

## Phase 1 - Application Foundation

Status: implemented.

Goal: maintain a small, typed, testable Python application foundation.

Actions:

1. Keep `realtimedatastreaming` as the package entrypoint.
2. Keep dependency management on `uv`.
3. Keep Ruff, mypy strict mode, pytest, coverage, and dependency audits green.
4. Keep runtime configuration typed and environment-driven.
5. Keep secrets outside source code.
6. Keep the application image minimal and reproducible.

Deliverables:

- importable package and CLI smoke test;
- typed settings and `.env.example`;
- unit-test, lint, typing, and coverage gates;
- minimal application container.

## Phase 2 - Ingestion And Data Quality

Status: implemented for the current source.

Goal: make source ingestion predictable, bounded, and privacy-aware.

Actions:

1. Fetch Random User profiles with explicit timeouts.
2. Apply bounded retries and backoff to transient failures.
3. Rate-limit source API calls.
4. Normalize source payloads into a typed profile.
5. Classify ingestion failures explicitly.
6. Validate profile structure and semantic quality.
7. Route invalid profiles with explicit rejection reasons.
8. Pseudonymize source identifiers and allowlist invalid-event payloads.

Deliverables:

- `RandomUserClient`;
- `NormalizedUserProfile`;
- `UserCreated` and `UserProfileInvalid`;
- quality validation and invalid-event builder;
- deterministic tests without external network calls.

## Phase 3 - Kafka Messaging And Contracts

Status: implemented for the current event flow.

Goal: publish events through Kafka with explicit schemas and observable delivery outcomes.

Actions:

1. Maintain a small topic catalog.
2. Store versioned Kafka JSON Schema artifacts.
3. Use topic-value Schema Registry subjects.
4. Configure reliable producer defaults including idempotence and `acks=all`.
5. Handle local producer queue pressure.
6. Support asynchronous, single-message synchronous, and batch synchronous publication.
7. Surface delivery timeout, failure, and missing-acknowledgement conditions.
8. Use the source identifier as the Kafka key where appropriate.

Deliverables:

- `UserProfileEventProducer`;
- `SchemaRegistryValueSerializer`;
- versioned event contracts;
- producer and contract tests;
- real Kafka and Schema Registry integration test.

## Phase 4 - Airflow Orchestration

Status: implementation foundation present.

Goal: orchestrate the pipeline when execution requires scheduling, retries, backfills, and operational ownership.

Actions:

1. Keep business logic outside DAG definitions.
2. Define schedule, retries, catchup, tags, and backfill behavior.
3. Manage Airflow connections and runtime secrets outside code.
4. Maintain DAG import and contract tests.
5. Document failed-run diagnosis and safe rerun behavior.

Deliverables:

- executable orchestration scaffold;
- retry and backfill policy;
- DAG import and Kafka contract tests;
- scheduler and failed-run application notes.

## Phase 5 - Spark Streaming

Status: implementation foundation present.

Goal: consume, validate, and route Kafka events through a distributed stream processor.

Actions:

1. Consume Schema Registry-framed `users_created` events.
2. Validate the supported schema identifier before deserialization.
3. Apply profile-quality rules.
4. Route accepted and rejected records to dedicated topics.
5. Maintain separate checkpoints for output routes.
6. Add event-time handling and deduplication when processing semantics are defined.
7. Support graceful restart and checkpoint recovery.

Deliverables:

- executable Spark Streaming job;
- Kafka source and output routes;
- schema-aware deserialization;
- checkpoint configuration;
- deterministic transformation tests;
- Kafka/Spark integration smoke test.

## Phase 6 - Cassandra Persistence

Status: planned.

Goal: persist queryable profile and quality views from explicit access patterns.

Actions:

1. Define query patterns before designing CQL tables.
2. Create versioned CQL schemas.
3. Make writes idempotent.
4. Define TTL and retention behavior.
5. Handle write failures without silently losing events.
6. Add schema and sink integration tests.

Candidate query patterns:

- latest valid profiles by ingestion time;
- valid profiles by country;
- invalid events by reason and processing time;
- quality counters by time window.

Deliverables:

- versioned CQL schema;
- Cassandra writer or Spark sink;
- idempotent write model;
- schema and integration tests.

## Phase 7 - End-To-End Application Validation

Goal: prove the functional data path across real service boundaries.

Actions:

1. Keep fast deterministic tests as the default test lane.
2. Keep external-service tests explicitly marked as integration tests.
3. Test Kafka publication and Schema Registry framing against real services.
4. Test Spark consumption, validation, and output routing.
5. Add source-to-Cassandra scenarios when persistence is introduced.
6. Cover accepted data, rejected data, schema failure, and delivery failure paths.

Deliverables:

- component integration lanes;
- complete application E2E lane;
- reproducible test data and expected outputs;
- failure-path assertions.

## Phase 8 - Integrated Application Pipeline

Status: planned.

Goal: connect the independently implemented modules into one executable, operational source-to-sink pipeline.

Actions:

1. Create an application ingestion entrypoint that fetches profiles through `RandomUserClient`.
2. Convert normalized source profiles into `UserCreated` events.
3. Apply profile-quality validation and build privacy-reduced `UserProfileInvalid` events.
4. Publish valid and invalid ingestion outcomes to their configured Kafka topics with confirmed delivery.
5. Replace the Airflow ingestion scaffold command with the real application ingestion entrypoint.
6. Connect Spark output routes to the Cassandra persistence layer.
7. Propagate correlation and operational context across ingestion, Kafka, Spark, and persistence boundaries.
8. Validate configuration, lifecycle management, retries, shutdown, and replay behavior for the assembled pipeline.
9. Run the complete Random User-to-Cassandra path through Airflow in a reproducible integration environment.

Deliverables:

- executable ingestion application service;
- Airflow DAG running real source ingestion and Kafka publication;
- connected Kafka-to-Spark-to-Cassandra processing path;
- documented module boundaries and runtime configuration;
- complete source-to-sink integration test;
- operational runbook for the assembled application.

## Application Delivery Order

| Increment | Capability | Exit criterion |
|---|---|---|
| 1 | Foundation and configuration | package, settings, tests, and image are reproducible |
| 2 | Ingestion and quality | source data is normalized and rejected safely |
| 3 | Kafka messaging | real schema-framed events are acknowledged by Kafka |
| 4 | Airflow orchestration | DAG scheduling, policies, imports, and rerun behavior are tested |
| 5 | Spark processing | real events are validated and routed with checkpoints |
| 6 | Cassandra persistence | query views receive idempotent writes |
| 7 | Full application path | source-to-sink success and failure scenarios pass |
| 8 | Integrated application | all modules run together through one operational entrypoint |

## Application Definition Of Done

The application roadmap is complete when:

1. Every event boundary has a versioned contract.
2. Source failures and invalid data have explicit outcomes.
3. Kafka publication confirms delivery for short-lived jobs.
4. Airflow schedules and reruns ingestion safely.
5. Spark validates and routes events with recoverable checkpoints.
6. Cassandra writes are idempotent and based on documented query patterns.
7. The complete source-to-sink path has reproducible integration tests.
8. Application behavior required by Reliability Consolidation is implemented and testable.
9. The ingestion, orchestration, messaging, streaming, and persistence modules are connected into one executable application pipeline.
